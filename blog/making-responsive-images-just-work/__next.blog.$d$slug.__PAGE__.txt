17:T700,<p>The responsive-image cleanup started as a performance task: downscale assets, add <code>srcSet</code>/<code>sizes</code>, and improve LCP. The bigger problem turned out to be maintainability.</p>
<p>Image behavior was spread across scripts and components with repeated conventions:</p>
<ul>
<li>variant naming assumptions,</li>
<li>duplicated variant-path assumptions,</li>
<li>multiple script aliases and legacy paths.</li>
</ul>
<p>That made drift easy. A renamed variant or new profile could leave an old path assumption behind. I replaced that with a simpler pattern: generate one manifest at build time (<code>src/generated/imageVariantManifest.json</code>) and use shared helpers to resolve variants before rendering.</p>
<h2>One manifest instead of scattered assumptions</h2>
<p><code>yarn image:variants</code> is now the canonical workflow. Lookup helpers read the generated metadata and pass resolved image paths and <code>srcSet</code> values into the shared <code>ResponsiveImage</code> component used for cover images and the homepage portrait. Inline Markdown images use the same manifest through the HTML conversion pipeline.</p>
<p>I also wanted to avoid manually creating every profile-specific variant when I added an image. For blog covers and inline Markdown images, the authoring path is now to add the source image, reference it in frontmatter or markdown, and run <code>yarn image:variants</code>.</p>
<h2>Stricter failure modes</h2>
<p>The manifest loader now rejects missing or empty required profile definitions (<code>cover.card</code>, <code>cover.hero</code>, <code>inlineContent</code>). Individual cover and inline variants can still fall back to the source image, so the hard failure protects the manifest schema rather than every cover or inline
