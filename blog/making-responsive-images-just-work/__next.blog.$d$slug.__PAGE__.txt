17:Tf8c,<p>I wanted images on this site to load faster by generating smaller versions and using <code>srcSet</code> and <code>sizes</code> to let the browser choose a suitable file. The scripts and components repeated assumptions about variant names and paths, so renaming a generated image meant updating every place that constructed its path.</p>
<p>I moved those assumptions into the generator and had it write a manifest alongside the images. This site exports static files for GitHub Pages, so the variants exist before deployment. During rendering, components and the Markdown pipeline look up those files in <code>src/generated/imageVariantManifest.json</code>.</p>
<h2>Generate files and metadata together</h2>
<p>For a blog cover, I add a WebP source under <code>public/assets/</code>, reference it in the post’s <code>coverImage</code> frontmatter, and run <code>yarn image:variants</code>. The same command discovers local images referenced in Markdown. <code>yarn build</code> runs it before the static export, so adding a post does not require a separate list of images to process.</p>
<p>The generator defines profiles for different uses: three card widths, two hero widths, and two inline-content widths. It uses those definitions both to generate the files with <code>cwebp</code> and to populate the manifest. Each source path maps to the available variants, with dimensions read from the files themselves. For example, the hero entry for this post’s cover is:</p>
<pre tabindex="0"><code><span><span style="color:#9ECBFF">"hero"</span><span style="color:#E1E4E8">: {</span></span>
<span><span style="color:#79B8FF">  "path"</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">"/assets/blog/making-responsive-images-just-work/cover-hero.webp"</span><span style="color:#E1E4E8">,</span></span>
<span><span style="color:#79B8FF">  "width"</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">1280</span><span style="color:#E1E4E8">,</span></span>
<span><span style="color:#79B8FF">  "height"</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">854</span></span>
<span><span style="color:#E1E4E8">}</span></span></code></pre>
<p>The manifest also records that the hero profile contains <code>hero-sm</code> and <code>hero</code>. A caller can request that profile using the original source path; it does not need to know the filename suffixes or repeat the widths. Changing the generator’s profile changes the metadata used to construct <code>srcSet</code> as well.</p>
<h2>Resolve by use, keep layout with the page</h2>
<p>Cover helpers select the largest available variant in the requested profile for <code>src</code> and build a width-based <code>srcSet</code> from the available entries. <code>ResponsiveImage</code> passes those values to a native <code>img</code>. For inline images, the Markdown conversion applies the same lookup before producing HTML, adding dimensions and lazy loading along with the responsive sources. The post itself keeps an ordinary Markdown image reference.</p>
<p>The manifest describes the files, while <code>sizes</code> remains with the rendering code that knows the layout. A thumbnail and a full-width cover can use the same source without claiming the same display width. This keeps layout decisions out of the generator while removing filename conventions from its consumers.</p>
<p>There is still a distinction between a broken manifest and a missing variant. The loader rejects missing or empty <code>cover.card</code>, <code>cover.hero</code>, and <code>inlineContent</code> profile definitions. An individual blog image can fall back to its source when no matching variant is available; fewer than two available variants means no <code>srcSet</code>. Those fallbacks keep a missing resize from becoming a broken image, but they can leave the original, larger file in use.
