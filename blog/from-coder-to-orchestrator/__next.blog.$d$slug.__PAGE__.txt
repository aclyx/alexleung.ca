18:T850,<p>In early 2024, I used AI mostly for snippets, error explanations, and small refactors. By 2026, I was handing agents larger tasks and spending more of my attention on constraints, review, and the edge cases they missed. Implementation could run in parallel, but the plans and finished changes still came back to me.</p>
<h2>Reviewing the plan before the code</h2>
<p>With Cline, I kept to straightforward work such as boilerplate, test scaffolding, and repetitive refactors. Larger tasks took too much prompt back-and-forth, and code that looked reasonable could still be wrong in ways that were hard to spot. In 2025, I switched to Claude Code and began asking for a plan before implementation.</p>
<p>Reviewing the plan gave me an earlier chance to challenge the scope. Plans were often overbuilt for the problem; questioning the approach before implementation meant I could address that without first reviewing the code it produced. But the agent would still report “done” before handling edge cases. Agreeing on a plan settled what to attempt, while reviewing the result was how I checked whether it had actually been done.</p>
<h2>Repository context and checkpoints</h2>
<p>Many mistakes came from missing repository context, so I keep architecture preferences, testing requirements, and coding conventions in the repository guidance. Those instructions carry decisions that apply across tasks. The task brief can then concentrate on the particular change, including its constraints and non-goals, instead of making the agent infer both the local conventions and the request at once.</p>
<p>I often separate planning from implementation and turn the brief into checkpoints, running build, lint, and tests at each one. That gives me intermediate results to inspect.</p>
<p>This works best when the repository records the context behind its decisions. Agents still struggle with undocumented history, and frequent tool calls and retries add to the cost of a session.
